# 已知架構限制：下游靜默回錯內容（HTTP 200）時，RCA 指到呼叫端

狀態：**不修，記為已知限制**（2026-11-14）。沒有改 `aiops/` 任何一行；新增的是死區測試 `tests/test_rca_silent_downstream.py`。

## 現象

下游服務回 200、耗時正常，但內容是空的或錯的；呼叫端解析時自己丟例外。

- 企業考卷 e1 的 E2 格（T 軌）：6 題都有通知，RCA 4 題第一名是呼叫端（真值是下游，記為「因果反指」）、2 題不指認。
- 隨機考卷 v2 的 empty 家族：因果反指 53%（`docs/FUZZ_EXAM_RESULTS.md`）。

## 為什麼現在解不了

`rca.root_cause.evidence` 的證據是 span：誰的自身耗時漲了、誰自己失敗。這種故障裡：

| | 下游 | 呼叫端 |
| :-- | :-- | :-- |
| 耗時 | 不變 | 不變 |
| span 狀態 | 成功（200） | 失敗，而且它底下沒有失敗的子 span = 自身錯誤 |
| 指標 | 沒有異常，所以不在事件群裡 | 錯誤數上升，告警 |

span 與指標都不記回應內容。這跟「下游完全正常、呼叫端自己新上的程式有 bug」留下的 span **逐筆相同**
（`test_silent_bad_response_and_caller_bug_leave_identical_spans`）。兩種原因在資料上不可分辨，
所以任何只看 span 的判準，都必然在其中一種指錯；現在的行為（指自身出錯的那個）在呼叫端 bug 時是對的。

## 沒有做的事，以及為什麼

- **沒有「呼叫端自身出錯就往下游推」的規則**：會把每一個呼叫端自己的 bug 都指到無辜的下游。
- **沒有讀錯誤訊息裡的服務名稱來改排名**：考卷的錯誤訊息剛好寫了下游的名字（`<下游> returned an empty result`），
  那是模擬器這樣寫的；真實系統的例外訊息不保證提到下游，用它改排名等於照考卷的字眼作答（CLAUDE.md §100.5）。
- 報告目前的樣子已經把線索交給人：「錯誤日誌」段落的第一名樣板就是呼叫端那句例外（E2 六題裡有通知且有日誌段落的都列出了），
  只是根因候選寫的是呼叫端。

## 要解需要什麼（都是通用機制，都還沒有資料可以驗證）

| 機制 | 需要的資料 | 現況 |
| :-- | :-- | :-- |
| 下游自己的「回應內容」症狀：回應大小、回傳筆數相對基準驟降，當成自身耗時、自身錯誤之外的第三種自身症狀 | span 帶 `http.response.body.size`、`db.response.returned_rows` 這類欄位（OTel 語意慣例裡是選填） | `SpanRecord` 沒有這些欄位，欄位對照沒有對應；真實資料（es-test 的 APM）有沒有這些欄位**沒查過** |
| 共同下游旁證：兩個以上互不相干的呼叫者同時自身出錯，而它們的共同點是都呼叫同一個沒有症狀的下游 | 現有 span 就夠 | 沒做。E2 的下游都只有一個呼叫者，考卷驗不到；只能當旁證（共用程式庫同時上版也會長這樣），不能當證明 |

兩個都是新功能，要做的話先查真實資料有沒有欄位、再登錄驗證方式；在那之前 E2 的分數維持原樣。

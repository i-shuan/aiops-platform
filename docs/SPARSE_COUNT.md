# detector.sparse_count：稀疏計數票

## 是什麼

平常幾乎都是 0 的計數序列（例如每 5 分鐘「整輪失敗幾次」），看「最近 `window` 個點一共幾筆」是不是比訓練期的發生率多太多。
模型是 Gamma-Poisson（負二項）：訓練期的筆數決定發生率的不確定性，分數 = −log10 P(這麼多筆以上)。
只判「變多」，不判「掉到 0」。不投票（`votes = False`），要單獨成立。演算法細節、常數來源與死區寫在
`aiops/stages/detectors/sparse_count.py` 的模組說明。

## 用在哪裡

只用在平台看門狗（`aiops/pipelines/watchdog/platform_watchdog.yaml` 的 `failures` 節點）：監控被排程的管線「整輪失敗」有沒有突然變多。
偵測演算法不給使用者用（CLAUDE.md §1.1 第 9 點），所以它不會掛在任何使用者管線上。

## 驗證狀態（照實寫，不要讀成「驗證過」）

- **只在合成的考卷上測過。** 下面兩個數字是主 session 轉述的（2026-11-15），我沒有重跑、也沒有看到那份考卷：
  - 已知題 L2：抓到 4/6。
  - 沒看過的新種子：抓到 2/6。
  - 兩者差距大（4/6 對 2/6），是過度擬合或樣本太少的訊號；**漏掉的題沒有查原因**。
- **參數沒有調過**：`threshold` 4、`window` 30、`min_events` 3 都是偵測器的預設值，看門狗也照用。
  threshold 4 的意思是「模型成立時，這種累積量出現的機率低於萬分之一」，是依模型算的，不是量出來的。
- **對看門狗這種新用途，在合成考卷上完全沒有驗證過。** 看門狗上的表現只有 `docs/WATCHDOG.md` 那份模擬紀錄的回放，
  那也不是真實資料：平台還沒上線，沒有真實的 `pipeline_runs`。
- 單元測試（`tests/test_sparse_count.py`）驗的是數學性質與介面（機率尾巴、過度離散、狀態存取、參數檢查），不是準確率。
- 在看門狗的實際設定上，第一版 YAML 的 `lookback_minutes`（120 分鐘 = 24 個 5 分鐘格）湊不滿一個窗口（30 格），
  這個偵測器每一輪都棄權、什麼都抓不到；是 `tests/test_watchdog.py` 的端到端測試抓到的，已改成 180 分鐘並加了測試擋住。

## 已知死區（來自模組說明）

- 有作息的稀疏事件（每天固定時段才失敗的排程）：發生率是整段平均，固定時段的群聚只靠過度離散修正，吸收不了時會在那個時段誤報。
- 訓練期本來就一直在失敗（不稀疏）：不判。
- 窗口內只有 1～2 筆：不判（`min_events`）。
- 掉到 0：不判（交給 `detector.rules` 這類下限規則）。

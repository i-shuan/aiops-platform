# 展示用截圖（2026-11-20，演練叢集）

三張都是從演練叢集裡那一台 Grafana 13.0.7 實際截下來的畫面（`scripts/grafana_screenshots.py`），不是合成圖。
平台是部署在叢集裡的版本（映像 `aiops-platform:v2c`），由排程每 5 分鐘自動跑。

**資料是模擬的**：MQ／CIM／AMHS 的指標來自 `scripts/line_sim`（回補 14 天＋即時），故障是手動注入的
「MQ 消費者全掉」骨牌（13:42～13:51 UTC），不是真實產線。

## 週報摘要

本週完成 AIOps 平台與 Grafana 的整合實測：使用者只要在 Grafana 告警規則貼上標籤，平台就會自動判讀該指標，
並把異常與根因標回 Grafana 圖表，不需另建網站。以模擬的產線 MQ 故障測試，3 分鐘內開出一張 P0 事故，
三個系統併成一張，根因推測為 MQ。

## 圖說

1. `01_aiops_incidents.png`——**事件群總覽**：平台判出的異常直接列在 Grafana 儀表板，分 P0、P1 與全部；
   每一筆有嚴重度、受影響的系統、RCA 根因，以及回到告警規則調整優先權的連結。
2. `02_line_metrics_rca.png`——**產線時序圖上的事故標記**：MQ 佇列暴增後 CIM 逾時、AMHS 搬運變慢，
   紅色區間是平台判定的事故範圍；滑鼠停在上面顯示「根因（依關係圖推測）：mq-broker」。
3. `03_rule_labels.png`——**使用者自己決定看什麼、多嚴重**：在 Grafana 告警規則貼 `aiops_detect`（交給平台判讀）
   與 `aiops_severity`（P0～P3），改標籤下一輪就生效，平台端不用改任何設定。

## 看圖時要知道的事

- 根因是「依關係圖推測」，不是有直接證據：產線設備沒有 trace，平台是依「CIM 依賴 MQ、AMHS 依賴 CIM」這兩條
  人工宣告的關係，加上誰最先異常來推的。
- 圖 2 的紅色區間到 22:00，故障其實 21:51 就移除了：漂移演算法看 30 分鐘的滾動平均，故障結束後還會再判一段時間。
- 圖 1、圖 2 上另有一張 P2 的 `rca-wip-worker`：那段時間沒有注入任何故障，是真實服務延遲的正常波動被判成異常
  （誤報）。沒有把它從畫面上拿掉。
- 截圖前清掉了四筆註記：那是剛部署時基準線用到含故障的資料、在正常資料上誤開的卡（含一張 P0）。
